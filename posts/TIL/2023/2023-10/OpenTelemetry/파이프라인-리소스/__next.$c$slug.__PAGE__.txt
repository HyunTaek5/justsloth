3:Td91,<h1>관찰 가능성 엔지니어링</h1>
<p>OpenTelemetry의 개념 - 파이프라인, 리소스</p>
<h3>OpenTelemetry의 개념</h3>
<ul>
<li>
<h4>파이프라인</h4>
<ul>
<li>각 시그널이 획득한 원격 측정 데이터가 유용하게 쓰이려면 저장/분석을 수행할 수 있도록 데이터 저장소에 저장이 필요하다.</li>
<li>시그널 구현체는 원격 측정 데이터를 생성/처리/전송할 수 있는 매커니즘을 제공한다.
<ul>
<li>Provider -> 생성기 -> 처리기 -> Exporter 순으로 처리 구조를 가진다.
<ul>
<li>Provider
<ul>
<li>설정 가능한 팩토리</li>
<li>원격 측정 데이터를 생성할 때 사용하는 엔티티에 애플리케이션이 접근할 수 있도록 한다.</li>
<li>SDK가 제공하는 기본 전역 프로바이더를 사용하거나, 애플리케이션에서 여러 개의 프로바이더를 설정할 수도 있다.</li>
<li>원격 측정 데이터가 생성되기 이전에 init 되어야한다.</li>
</ul>
</li>
<li>생성기
<ul>
<li>애플리케이션을 계측하고, API를 사용하는 동안 상호 작용하는 대상</li>
<li>계측하는 시그널에 따라 다른 이름을 가지게 된다.
<ul>
<li>이름은 서로 다르지만, 원격 측정 데이터를 생성하기 위해 존재한다는 목적을 동일하다.</li>
<li>추적시그널 = 추적기</li>
<li>메트릭 시그널 = 미터</li>
</ul>
</li>
</ul>
</li>
<li>처리기
<ul>
<li>데이터의 내용를 추가로 수정할 수 있다.</li>
<li>데이터가 어떤 빈도로 처리되야 하는지, 어떻게 추출되어야 하는지를 결정한다.</li>
</ul>
</li>
<li>Exporter
<ul>
<li>원격 측정 데이터가 애플리케이션 컨텍스트를 빠져나가기 전에 거치는 마지막 단계</li>
<li>OpenTelemetry의 내부 데이터 모델을 Exporter가 이해한 형식으로 변환하는 역할</li>
<li>다양한 export 방식 및 프로토콜 지원
<ul>
<li>OpenTelemetry 프로토콜</li>
<li>콘솔</li>
<li>예거</li>
<li>집킨(Zipkin)</li>
<li>프로메테우스</li>
<li>OpenCensus</li>
</ul>
</li>
</ul>
</li>
</ul>
</li>
<li>원격 측정 파이프라인의 각 컴포넌트는 중요한 원격 측정 데이터가 누락되지 않도록 애플리케이션 코드 초반부에 init하는 것이 일반적이다.</li>
</ul>
</li>
</ul>
</li>
<li>
<h4>리소스</h4>
<ul>
<li>애플리케이션 전반에 걸쳐서 원격 측정 데이터를 의미있고, 일관성있게 만드는 핵심 컴포넌트</li>
<li>서로 다른 시그널에 적용된 일련의 속성</li>
<li>원격 측정 데이터의 출처를 식별할 때 사용
<ul>
<li>출처가 서버인지, 컨테이너인지, 함수인지</li>
<li>데이터 분석 시 동일 리소스 내에서 발생한 서로 다른 이벤트를 연결하는데 사용할 수 있다.</li>
</ul>
</li>
<li>리소스 속성은 데이터를 백엔드 시스템으로 보내기 전 시그널로 부터 전달받은 원격 측정 데이터를 추출할 때 추가된다. 보통 애플리케이션 시작 시 설정되고, Provider와 연결된다.</li>
<li>애플리케이션 수명 주기 동안 변하지 않는 것이 일반적이다.</li>
<li>리소스 속성
<ul>
<li>service.name : 서비스명</li>
<li>service.version : 서비스의 버전 식별자</li>
<li>host.name : 서비스가 작동하고 있는 호스트명</li>
</ul>
</li>
<li>리소스와 리소스 감지기는 시맨틱 표기법을 따름</li>
</ul>
</li>
